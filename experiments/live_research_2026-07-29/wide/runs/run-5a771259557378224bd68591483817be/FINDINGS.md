## Latest composed view

Resolution: **partially_answered** (composed at formal sequence 281; supersedable — no answer is final).

> For an append-only event log with at-least-once delivery, safety is categorically impossible for its writers. Safe methods forbid all server state mutation, and writers must mutate the log by appending events. Because writers always expect and request a state change, the log cannot require safety regardless of deduplication strategy.
> The log instead requires idempotence of its writers. At-least-once delivery retries writes that may have already succeeded, and idempotence guarantees that repeated identical requests yield the same effect as a single request. The causal mechanism for preventing duplicate events is deduplication via a stable operation key, sequence number, or content hash that lets the append path detect and discard replays.
> There is an unresolved rivalry over whether the log requires RFC 9110 idempotence simpliciter or a stronger, log-specific property. One position holds that the log requires idempotence in the RFC sense; the opposing position holds that the log requires a property distinct from or strictly stronger than RFC idempotence, because RFC 9110 idempotence is order-insensitive and defined over individual HTTP method semantics rather than over ordered sequences of operations with causality.
> The record cannot determine two definitional matters from RFC 9110 because no verbatim source text is available: whether the RFC explicitly states that safe methods are a subset of idempotent methods or merely implies it; and whether idempotence is defined over the observable response, over server state, or over both. The latter distinction matters because if idempotence is defined over responses only, the event-log deduplication requirement is a separate, stronger property.
