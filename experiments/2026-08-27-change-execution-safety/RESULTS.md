# RESULTS — execution safety (2026-08-27)

Honest ledger. What the record shows, and the residue.

## 2026-08-27 — asked whether it was safe to switch on; it is not, and the reason is not where anyone was looking

The operator asked one question: model-authored code execution and
simulation appear to be off, is it safe to switch them on, and if so
switch them on. The switch was pre-authorized conditional on a SAFE
verdict. **The verdict is NOT PROVEN and nothing was switched on.**

**What the census found (SPEC.md R1).** Five paths can execute code; two
execute MODEL-AUTHORED code. Row 2, the `sandboxed_python_v1` simulation
runner, is off exactly as commit `74d9f71ca` recorded — the default
`runner_profile="simulation.declarative.v1"` refuses it, while the same
policy binds a Python toolchain that profile can never dispatch to. Row
3, the code-testing channel, is **on, ungated, and has been executing
model-authored Python the whole time**. So the operator's premise —
"it's been off this whole time" — is right about one road and wrong
about the other, and the two roads are not the same road.

**What the assessment found (SAFETY.md R2).** Of the five containment
properties, three hold and are demonstrated: no network, bounded wall
time, bounded memory. Two do not:

- **(d) file confinement — ABSENT.** Model-authored Python wrote a file
  at an absolute path outside the ephemeral scratch directory. The
  simulation returned `pass`.
- **(e) no privilege beyond the harness process — ABSENT.**
  `os.system('true')` returned 0 from inside the "contained" runner.

Both come from ONE hole. Both guards — `contained.py`'s frozen worker and
`oracle.py`'s stricter `_guard` — reject leading-underscore attributes.
`gi_frame`, `f_back` and `f_globals` have no underscore, so a running
generator hands model code the worker module's own globals and the real
`builtins`. A denylist over attribute names is the wrong shape for the
job; that is the finding, not the specific three attributes.

**The finding nobody asked for.** The same escape works on the
code-testing channel, which is ON today — and that channel has **no
network namespace at all**. The probe opened a real TCP connection to
1.1.1.1:80 from inside the sandbox while the exec-oracle commitment
returned `pass`. So the containment ordering is the reverse of what the
question assumed: **the channel that is off is the better-contained one.**

**What held, and it matters.** Every attack the design anticipated was
stopped: `import socket`, `__import__`, the dunder walk, `open()`, the
infinite loop, the C-level int bomb, the memory bomb. And the network
namespace survived a full language escape with arbitrary subprocess
spawning available — the one property that never depended on the
language boundary is the one that held under it. The committed
containment suite is green here with nothing skipped. This is one hole in
one guard, not a design that was never taken seriously.

**Method note.** The verdict rests on a re-runnable, self-cleaning
reproduction (`proof/containment_probe.py`), not on reading the code and
reasoning about it. That was the operator's own standing law doing the
work — "tokens are cheap; the agent is not… prefer evidence generated by
live runs" — applied offline. Reading `contained.py`'s docstring would
have produced the opposite verdict: it states all five properties, in
good faith, and two of them are not true.

## Residue — what is NOT established

- **That G1 is the only hole.** One hole was found and it is trivially
  exploitable. A second probe against the same denylist shape may find
  another. The fix specified in PARKED.md P1/P2 is an AST-node allowlist
  precisely because enumerating holes is not a strategy.
- **Anything about hosts where `containment_available()` is False.**
  There the contained runner refuses to run at all, which is correct —
  but the code-testing channel keeps running with no namespace anywhere.
- **That the escape was ever exercised in a live run.** No committed root
  was examined for it, and nothing suggests glm-5.2 attempted anything of
  the kind. The risk assessed here is capability, not incident.
- **That switching on is unsafe in principle.** It is unsafe *today*.
  Three of five properties already hold; PARKED.md P2 is a bounded piece
  of work, and the operator's authorization survives it — "If so switch
  both on" remains standing for the tranche that closes the gap.

"Accepted does not mean true." A green
`tests/test_contained_simulation_runner.py` meant only that the
anticipated attacks had been anticipated. It is still green.
