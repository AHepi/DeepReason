=== RUNS 1 AND 2 — the hashing fallback, kept because they mislead ==========
Both ran WITHOUT warming the embedder, so `_equivalent` fell back to hashing.

RUN 1: hv_spot_check hv=0.0; run_hv_floor (no battery) -> FAIL, s_hat 1.0.
       2 work items. verify_root 0 violations.
RUN 2: hv_spot_check hv=0.0; run_hv_floor (no battery) -> PASS, hv 1.0;
       with battery -> FAIL. 3 work items. verify_root 0 violations.

The SAME no-battery target came back FAIL in run 1 and PASS in run 2, and run 2
additionally got the battery case backwards. An edit survives only if it passes
the battery AND is judged INEQUIVALENT to the original, so the equivalence
surrogate decides half of every verdict -- and on the hashing fallback it
decides it badly. Run 3, with the neural backend, gets both cases right.

THE RULE THIS ESTABLISHES: a live `hv` number taken without
`deepreason embedder-warmup` is not a measurement. CLAUDE.md already says to
warm the embedder in the setup phase of any session that runs the harness; this
is what skipping it costs -- not an error, not a fallback notice anyone would
chase, just verdicts that quietly flip.

=== A SCAFFOLD TRAP, worth keeping (cost this check one run to find) ========
A root whose `run-manifest.json` is not ON DISK makes `verify_root` return early
with an empty controller-v3 context, so every transactional call fails
`workflow-call-pairing` with "transaction call is not its durable provider
result". Three violations, all meaningless, and they read exactly like a
dispatch defect. The root must be built properly -- run input first, manifest
compiled against its digest, both bound -- before verify_root says anything
about a transaction at all.
