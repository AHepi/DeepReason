### Which of those 45 verbs touch results or status

| Verb | What it actually reads | Covers which of R6–R10 |
|---|---|---|
| `status [--json]` | **provider/qualification readiness — NOT a run's outcome.** `_cmd_status` (`cli/main.py:1652`) reports whether a model is qualified and what the next action is. Reads no run root. | none |
| `findings [--json]` | `findings.findings_summary(root)` — question, `run-status.json` subset (state/stop_reason/message/cycle/token_spend/token_limit), positions by status (accepted/refuted/suspended), rivalries, criticism ledger, branches, capability ledger | **R6 partly** (state, stop_reason, cycle, token spend/limit — no run id), **R7 partly** (accepted/refuted/suspended lists; no survivor count, no frontier) |
| `watch [--once] [--interval]` | live `progress.jsonl` / `run-status.json` tail via `TEXT_RUN_SERVICE.watch` | R6 partly, live only |
| `report` | P6 eval report (valid-JSON rate, attack validity, trial guard) | none of R6–R10 directly |
| `frontier` | the problem frontier from replay state | R7 partly (frontier) |
| `signals` | per-signal-kind counts over the whole log, with registry meanings (`signals.SIGNALS`/`PREFIXES`) | **R8 partly** (`trial-*` counts are here, but mixed into ~90 other kinds) |
| `capture` | both-surface capture dashboard | none |
| `export --out` | writes surviving deliverables to a directory | R7 adjacent (survivors, but as files) |
| `why <id>` / `evidence <id>` / `theory <id>` / `prose <id>` / `trace <id>` | per-artifact drilldown | none (single-artifact scope) |
| `narrate` | event log as prose | none |
| `blob <ref>` | raw blob dump | none |
| `explain-error <code>` | `error_catalog.lookup` gloss for a typed code | the surface R13 must extend |
| `amend` / `continue` / `cancel` | mutate a run; not readers | R10 adjacent (they are what the amend-readiness fact is FOR) |

**Nothing prints a run id.** `run-status.json.run_id` exists on disk; no verb
surfaces it.
**Nothing prints the `verify_root` verdict.** `REPLAY_VALIDATION.json` sits in
86 of 107 committed roots; no verb reads it.
**Nothing prints amendment epochs or terminal validity.**

### The two discoverability traps this census confirms (C1, C2)

1. `deepreason status` is provider readiness, not run status. A session looking
   for "the status of my run" reads the `--help` line "show provider and V6
   qualification readiness", finds it is not what it wants, and has nowhere
   else to go — `findings`' help line says "reader-facing findings summary:
   rivalries, refutations, suspended positions, side branches, criticism and
   capability ledgers — all replay-derived", which never uses the words
   *result*, *outcome*, or *status*.
2. `--root` is a GLOBAL option that precedes the verb (`deepreason --root R
   findings`), not a per-verb one. A session that writes `deepreason findings
   --root R` gets an argparse error, which is exactly the "grepping for flags
   that don't exist" loop C1 names.

`check: python -c "import argparse; from deepreason.cli.main import build_parser; p=build_parser(); s=[a for a in p._actions if isinstance(a,argparse._SubParsersAction)][0]; assert 'results' not in s.choices"` — true at census time; the acceptance test in SPEC.md inverts it.

## 4. R4 verdict — what already exists, and what `results` must therefore do

**The fix partly exists.** `findings.findings_summary` is a working, tested,
replay-derived reader that already answers about half of R6 and part of R7. It
is not discoverable (its help line never says *result*), it omits the run id,
and it knows nothing of verification, amendment epochs or terminal validity.

Therefore, per R4 ("the fix is surfacing and completing it, not duplicating
it"):

- `results` **calls** `findings_summary` for the facts that reader already
  derives — positions by status, the question, the `run-status.json` subset.
  It does not re-implement replay-derived status counting.
- `results` **adds** the four readers nobody has: run identity, verification
  verdict, adjudication counts, amendment/terminal readiness. Each is a small
  pure function reading one durable file or the log.
- `findings` keeps its behaviour byte-for-byte. Nothing is renamed, retired or
  moved; `results` is additive.

## 5. Census findings that are NOT this tranche's work

- **`findings` reads a run root but is not in `_ROOT_ADMISSION_COMMANDS`.**
  `DR-SUB-application`'s prose says "Every CLI verb that touches an existing run
  root passes through one V6 gate", which is over-broad: `findings` is an
  exception today, and `results` will be a second one by design (a reader that
  refused pre-V6 roots would refuse exactly the roots a session most needs to
  inspect — 11 of the committed roots raise
  `UnsupportedRunManifestVersionError`). The map sentence is corrected in this
  tranche's implementation commit under R22; the question of whether `findings`
  *should* be admitted is a design question for another tranche → `PARKED.md`.
- No committed document instructs a session to retrieve results via a
  nonexistent flag (`grep -rn "deepreason results\|--results\|results.json"
  docs/ .claude/ README.md` → no hits at census time), so R23's errata trigger
  does **not** fire. Recorded as a negative result, per the honest-ledger rule.
